# plan

実装計画を、意図・経路・決定の層に分けて立てる。恒久的に残す意図と決定を固定文書へ、流動する経路と分解を issue へ振り分け、実装が固まった時点で as-built として文書へ落とす。各段は「実際に何をしたいのか」を意図で書き、型名・関数名・具体定数などの実装語で圧縮しない。

## 適用境界

- 適用する: 機能・マイルストーンの実装計画、ロードマップの組み立て・組み直し、作業の issue 分解、実装経路の見直し
- 適用しない: 1〜2 ファイルの自明な変更（そのまま実行）、確定済み計画の実行（implement スキル）、完成した文書の執筆（write-docs スキル）

要件・スコープ・成功基準が固まっておらず、意図・層分け・スライスのいずれかを仮定で埋めることになる段階では、ユーザが起動するスキルである grill-me の実行を提案し、判断を仰ぐ。

## 手順

1. 意図を先に言語化する: 各段が「実際に何をしたいのか」を、型名・関数名・具体定数を使わずに書く。実装語で意図を圧縮しない（要件が実装手段の裏に隠れたら兆候）。
2. 層へ振り分ける:
    - 意図（何を・なぜ）: 仕様・コンセプト文書。まだ存在しないものの目的。
    - 決定・不変条件（なぜその判断か）: decision issue（ADR 形式。論点・選択肢・決定と理由・影響範囲）。着手前に合意が要るものはここで固める。
    - 経路・分解・命名・具体値（どう作るか）: 実装 issue。流動させ、固定文書へ先取りしない。
3. 縦スライスに刻む: 層を横に積み上げず、コア機能を貫く最小の一本から切り出す。各スライスは疎結合（未完成の部分に依存せず単独で成立する）で、単体で検証できる（単体テスト・動く成果物のデモなど、確かめ方は対象領域による）ことを満たす。全体を一括で固めず、次に作る一歩の粒度で計画する（大きな一括計画は文脈が溢れて破綻する）。
4. issue へ落とす: 各スライスを自己完結した issue にする（会話の文脈なしで implement スキルがそのまま実行できる、前提込みの粒度）。ロードマップ issue に依存順を書く。
5. 文書は追従に留める: 固定文書には意図・決定・不変条件だけを置く。経路・命名・具体値は issue とコードに置き、実装が固まった時点で write-docs スキルを通して as-built として文書へ反映する。

## 制約

- 実装語（型名・関数名・具体定数）を固定文書へ先取りしない。バインドは最も下の層（issue → コード）で行う。
- スコアリングや重み付け式などのセレモニーを持ち込まない（点推定は人にも LLM にも不確実で、割に合わない）。
- 計画の実行・コミットはしない（実行は implement、コミットは commit スキル）。
- 決定の根拠は decision issue に、変更の理由は commit ログに、現在の事実は文書に置く（CLAUDE.md の責務分担に従う）。
