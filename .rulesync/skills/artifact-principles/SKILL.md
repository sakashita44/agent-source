# Artifact Principles

## 実装に関する成果物

- コードは実現方法を表す
- テストは期待する振る舞いを表す
- 変更履歴は、各変更の内容と、その変更に固有の理由を後から追跡できる記録として用いる
- コードコメントは、外部に起因する非自明な背景を表す。実装方法の単なる言い換えは行わない

コメントの対象は、コードの外部にある事情に限る。外部仕様の制約、他システムの既知の不具合への回避策、規格や法令が定める値、計測により判明した性能上の理由などが該当する。

コード自体のわかりにくさはコメントで補わず、命名の変更、関数・変数・クラスの抽出、型付け、再設計によって解消する。採用しなかった選択肢は、コメントには書かず、[判断の記録](#判断の記録)に従って記録する。

コメントは実装とは別の工程で書く。実装しながら書くコメントは、作成者自身には何が非自明であるかが見えにくいため、実装内容の単なる言い換えに陥りやすい。

## 計画と知識に関する成果物

情報は、時点に依存しない内容と、開発の過程に属する内容に分けて置く。

| 置き場所 | 種類 | 内容 |
| --- | --- | --- |
| リポジトリ | 規範 | 要求、目的、コンセプト、保証する範囲。仕様書とコンセプト文書に書く |
| リポジトリ | 現行の事実 | コード、型、テスト、設定、利用方法の説明、公開 API。実装として成立した内容を表す |
| Issue | 判断の過程 | decision issue に、判断、理由、前提条件、採用しなかった案を記録する |
| Issue | 開発の管理 | 作業 Issue に、流動的な実装経路、作業分解、順序、実装中に調整する具体値を記録する。decision issue の索引やマイルストーンの管理が必要な場合は、メタ Issue を置く |

成果物の責務は置き場所ではなく役割に基づいて判断する。仕様書とコンセプト文書は、実装の前から目指す状態を定めてよい。これらは置き場所にかかわらず採用済みの意図、目的、期待する振る舞いを表し、実装の進捗に合わせて内容を変更しない。要求そのものが変わった場合は改訂する。

上位の成果物では意図を直接書く。型名、関数名、暫定的な定数などの実装語で意図を圧縮せず、具体化は Issue やコードに近い層で行う。

設計文書では、実装の型、関数、分岐、処理順を擬似コードで模写しない。模写は実装とは別に更新される第二の実装となり、同じ内容を二重管理することになる。具体的な実装が必要な場合は、実コードを前提条件とともに参照する。

設計・仕様文書では、読者が文書の責務と規定する内容を判断するために必要な場合、説明または規定する対象、設計上の責務、適用範囲、隣接する成果物との境界を冒頭に置く。

## リポジトリ内の成果物の自立

リポジトリ内の成果物には、進捗、計画、検討の経緯など、開発の工程に関する情報を含めない。内容を変更しないという意味ではない。成果物は、完成した時点でも成立する目指す状態と、実装として成立している事実だけを表す。時点に依存する表現の規則は `writing-principles` の「時間と事実」に定める。

作業ツリーのコード、コメント、文書、設定は、そのプロジェクト自身の Issue や PR を読まなくても理解できるようにする。それらへの参照は書かず、課題の追跡は Issue で行う。外部のプロジェクトの Issue は、不具合の回避策の根拠など外部の事実として参照してよい。Issue からリポジトリ内のファイルやコミットを参照することは認める。コミットメッセージと PR description は変更履歴に属する成果物であり、この規則の対象外とする。CI の設定や Issue テンプレートなど、GitHub の機能を使うための設定も同様に対象外とする。

リポジトリ内の文書の `TODO:` は、実装が確定してから書く利用方法や公開契約など、文書の未記入部分に限って置く。検討課題、作業計画、Issue への参照は `TODO:` にせず、Issue で扱う。`TODO:` を置くためだけの文書は作らない。

## 文書の新設と更新

永続文書は、既存のコード、型、テスト、設定、README、要求文書では果たせない役割がある場合に限って作る。設計を検討した結果を保存するためだけの文書は作らない。実装に近い詳細設計は必要に応じて Issue で検討し、成立した結果をコードとテストに表す。実装済みの公開仕様や複雑な利用手順など、独立した説明が必要な場合は文書を追加してよい。

設計判断を記録しただけでは、文書の更新を求めない。利用方法や公開契約は、実装の際に文書へ反映する。

不要になった文書は、非推奨として残さない。必要な情報を、その役割に合う成果物へ移したうえで削除する。

## 判断の記録

決定は、その時点の前提に基づくスナップショットである。前提が変化すれば決定は効力を失う。

判断の記録先は一箇所に集める。Issue で計画と判断を管理するプロジェクトでは、判断、理由、前提条件、採用しなかった案を decision issue に記録する。リポジトリ内の ADR は原則として用いず、リポジトリの規約が求める場合に限って用いる。

前提条件は判断とその理由とともに記録する。前提条件を記録しないと、前提の変化を後から検知できず、効力を失った決定に従い続けることになる。

過去の決定は当時の前提に基づく記録として残し、書き換えない。決定を見直す場合は、新しい decision issue で改訂する。

## 参照の到達可能性

Issue、PR description など、リポジトリの外部から閲覧される成果物には、ローカル環境にしか存在しないファイルへの参照を書かない。他のデバイスや閲覧者から参照できず、その成果物自体が読者にとって不完全な情報となるためである。

判断に必要な内容は成果物自体に埋め込む。埋め込む分量が過大な場合は、判断に必要な部分のみを抽出する。埋め込みを目的として、作業用の中間生成物を対象リポジトリに含めない。

## 中間ファイルの置き場所

調査記録、下書き、生成物の比較など、成果物とならない中間ファイルは、AI 側の一時領域に置く。対象リポジトリへ置くのは、ユーザーからの指示がある場合に限り、置き場所は対象リポジトリの `tmp/` とする。

## 二重管理の回避

同一の規則、仕様、定義、判断は一箇所に定めて一元管理する。他の成果物には、その場での判断に必要な要点と、参照が必要となる条件を伴う規定元への参照のみを書く。メタ Issue にも判断の内容を複写しない。

仕様書、要求文書、設計文書は、採用済みの規則、要求、適用範囲、設計内容を定める文書となり得る。文書が決定済みの内容を「定める」「規定する」ことと、担当者または役割が設計値や採用対象を選ぶことを区別する。
