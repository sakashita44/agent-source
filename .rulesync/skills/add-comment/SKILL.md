# Add Comment

コメントの内容を、実装していないエージェントに決めさせ、返ってきた提案を適用する。

コメントの是非は、実装の記憶を持たない立場でしか判定できない。実装した本人、または実装を指示したオーケストレータがこの手順を自分で実行しても、判定の前提が成立しない。このSkillの本体は委譲であり、何を書くかを自分で決めない。

委譲先はファイルを編集しない。適用はこのSkillが行う。編集の権限を渡さないことで、対象範囲の外への変更と、コードの動作が変わる書き換えが起こらない。

委譲の作法は`subagent`に従う。

## 手順

1. 対象の範囲を確定する。差分を対象とする場合は変更したファイルと範囲を、既存コードを対象とする場合は対象のファイルまたはディレクトリを定める
2. `write-comments`サブエージェントを起動する。渡すのは次に限る
    - 対象の範囲。ファイルのパスと、差分であればその範囲
    - コメントの理由を特定するために参照してよい情報源。関連するIssue、外部仕様のURLなど
3. 実装中に検討した内容、採用しなかった案、なぜその実装にしたかを渡さない。渡すと、委譲先が実装者と同じ視点になり、独立した判定にならない
4. 返ってきた提案を確認し、採るものを選ぶ
5. 選んだ提案を対象ファイルへ挿入する
6. 置かれたマーカーのうち、実装者として理由を答えられるものを補う

## 提案を採らない条件

- 対象範囲の外を指している
- 既存の行を書き換える内容になっている
- 実装方法の言い換えである
- コードを読めば分かる内容である
- 理由がコードの内側にある。この場合は、コメントではなく改名、抽出、型付け、再設計として扱う

採らなかった提案は、理由とともに報告する。

## 報告

委譲した範囲、挿入したコメント、採らなかった提案とその理由、残ったマーカー、削除を提案された既存コメント、設計で解消すべきと報告された箇所を示す。マーカーが残っている場合は、誰が補うかを明示する。
