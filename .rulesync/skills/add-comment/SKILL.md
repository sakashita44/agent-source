# Add Comment

実装した本人とは別の立場で、コードへコメントを書く。実装中の判断を知らない状態で読み、コードから読み取れない理由だけを残す。

実装しながら書くコメントは、書いた本人には自明でない箇所が見えないため、実装の言い換えになりやすい。読んだだけで分からない箇所を判定するには、実装の記憶を持たない立場が要る。

新しく書いたコードにも、既存のコードにも適用できる。

## 守備範囲

コメントの対象は、コードの外側にある事情に限る。

- 外部の仕様、プロトコル、規格、法令が定める制約と値
- 他システムやライブラリの既知の不具合への回避
- プラットフォームの挙動に由来する非自明な順序や条件
- 計測で判明した性能上の理由

自分たちのコード内の分かりにくさは、コメントで補わない。改名、抽出、型付け、再設計で解消する対象として報告する。長い正当化を要する箇所は、コメントが必要なのではなく設計が要る。

採用しなかった選択肢は、コメントではなく変更履歴とdecision recordへ置く。詳細は`artifact-principles`に従う。

## 手順

1. 対象を確定する。差分を対象とする場合は、追加または変更された範囲を読む。既存コードを対象とする場合は、対象ファイルと関連モジュールを読む
2. コメントを要する箇所を挙げる。読んだだけでは理由が分からず、その理由がコードの外側にある箇所に限る
3. 各箇所の理由を、コード、テスト、変更履歴、Issue、外部の仕様から特定する
4. 理由を特定できた箇所へコメントを書く
5. 理由を特定できなかった箇所へマーカーを置く
6. 既存のコメントのうち、実装の言い換えになっているものと、守備範囲を外れるものを報告する
7. 設計で解消すべき箇所を報告する

## マーカー

理由を特定できない箇所には、次の形式で置く。補うのは実装者または利用者である。

```text
TODO(reason): <何が非自明か。分かっている手掛かり>
```

推測で理由を書かない。特定できないことを残すほうが、誤った理由を残すより損失が小さい。

## 制約

- 既存のコメントを削除しない。削除の判断は利用者が行う
- コードの動作を変更しない。コメントとマーカーの追加だけを行う
- 実装方法を言い換えるコメントを書かない
- 各行に説明を付けない。読んで分かる箇所へ書かない

## 報告

書いたコメント、置いたマーカー、削除を提案する既存コメント、設計で解消すべき箇所を、それぞれ対象箇所とともに報告する。
