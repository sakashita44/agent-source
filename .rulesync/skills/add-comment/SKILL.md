# Add Comment

コメントの内容を、実装を担当していないエージェントに決定させ、返された提案を適用する。

コメントの是非は、実装の記憶を持たない立場でしか判定できない。実装した本人や、実装を指示したオーケストレータがこの手順を自身で実行しても、判定の前提が成り立たない。この Skill の本体は委譲であり、記述内容は自身で決定しない。

委譲先はファイルを編集しない。適用はこの Skill が担う。編集権限を付与しないことで、対象範囲外への変更や、コードの動作が変わる書き換えを防ぐ。

委譲先の選択と委譲の作法は `subagent` に従う。

## 手順

1. 対象の範囲を確定する。差分を対象とする場合は変更したファイルと範囲を、既存コードを対象とする場合は対象のファイルまたはディレクトリを指定する
2. `subagent` に従って委譲先を選定し、`write-comments` の定義に沿ってコメントの提案を依頼する。提供する情報は以下に限る
    - 対象の範囲: ファイルパスと、差分であればその範囲
    - コメントの理由を特定するために参照してよい情報源: 関連する Issue や外部仕様の URL など
3. 実装中に検討した内容、採用しなかった案、なぜその実装にしたかの理由は提供しない。提供すると、委譲先が実装者と同じ視点になり、独立した判定ができなくなる
4. 対象ファイルが委譲前から変更されていないことを確認し、委譲先から返された提案の中から採用するものを選択する
5. 選択した提案を対象ファイルへ挿入する
6. 配置されたマーカーのうち、実装者として理由を説明できるものを補う

## 提案を採らない条件

- 対象範囲外を指している
- 既存の行を書き換える内容になっている
- 実装方法の言い換えである
- コードを読めば分かる内容である
- 理由がコードの内部にある。この場合はコメントではなく、改名、抽出、型付け、再設計として扱う

採らなかった提案は、理由とともに報告する。

## 報告

委譲した範囲、挿入したコメント、採らなかった提案とその理由、残ったマーカー、削除が提案された既存コメント、設計で解消すべきと報告された箇所を示す。マーカーが残っている場合は、誰が補うかを明示する。
