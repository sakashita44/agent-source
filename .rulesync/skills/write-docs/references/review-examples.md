# レビュー例

規則の適用可否に迷ったとき、またはレビューで違反を説明するときに参照する。通常の執筆では読み込まない。

## 読者からの独立性と導線

### 時間と変更履歴

- Bad: `現在、このコマンドは新しい認証方式に対応している`
- Good: `このコマンドは OAuth 2.0 に対応する`
- Bad: `従来の 300 mm から 350 mm に変更した`
- Good: `アーム長は 350 mm`
- 境界: CHANGELOG、リリースノート、ADR、移行手順では変化を書いてよい。版、日付、移行元、移行先を示す

### 導線と参照

- Bad: `詳しくはデプロイ手順を参照する`
- Good: `本番環境へ公開するときは、デプロイ手順を参照のこと`
- Bad: `下記を設定する`
- Good: `「認証設定」の各項目を設定する`
- Bad: `[こちら](configuration.md)`
- Good: `[認証設定](configuration.md)`
- 境界: 位置語を識別名へ添えることは許容する。対象を位置語だけで示さない

### 正本と局所要約

- Bad: README と運用手順へ、同じ認証規則の全文を複製する
- Good: README には開始に必要な認証条件だけを要約し、資格情報を設定するときに認証規則の正本へ案内する
- 境界: 局所要約は参照先を開かずにその場の判断または行動ができる範囲に限る。正本と同等の規則集合を再掲しない

## 構造と表現

### 階層と分類

- Bad: 前提概念と、その概念の中でのみ意味をなす項目を同じ見出しレベルに置く
- Good: 前提概念を上位、その概念へ依存する項目を下位に置く
- Bad: 分類と、その分類に属する具体例を同一階層に置く
- Good: 分類基準を先に示し、具体例を該当する分類の下位に置く
- 境界: 用語定義、チェック項目、選択肢など同種の語の列挙は、5 項目以上でも分割を要さない

### 対比と不在

- Bad: `設定ファイルは YAML ではなく TOML で記述する`
- Good: `設定ファイルは TOML で記述する`
- 境界: `ID は連番ではなく UUID を用いる` のように、読者が想定する自明な既定を外す意図が誤解を防ぐ場合は対比を許容する
- Bad: 温度補正を期待しない文脈で `本仕様では温度補正に言及しない`
- Good: 何も書かない
- 境界: 読者が温度補正を当然期待する場合は、対象外とする理由と、必要なら別の記録先を示す

### 見出しと強調

- Bad: `課題（現状に照らした）`
- Good: `現状の課題`
- Bad: `詳細`、`その他`、`今回の場合`
- Good: `認証エラーの診断`、`対応するデータ形式`
- Bad: 地の文中の太字やイタリックだけで重要性を示す
- Good: 見出し、リスト、インラインコード、文の順序で重要性を示す

### 日本語の終止と動詞

- Bad: `この設定は必要である`
- Good: 設定が必要になる条件と、読者が行う操作を直接書く
- Bad: `本番環境へデプロイする場合は、事前に手順書を参照すべきである`
- Good: `本番環境へのデプロイ前に、手順書を参照のこと`
- Bad: `実行前に必要なのは設定値の確認である`
- Good: `実行前の確認事項: 設定値`
- Bad: `設定ファイルは認証情報を持つ`
- Good: `設定ファイルに認証情報を収める`
- Bad: `Profile は識別子を割り当てる`
- Good: `識別子を割り当て、Profile へ記録する`
- Bad: Module 設計の流れが明らかな各文で、`Module 設計者は` を機械的に反復する
- Good: `利用する IF とその各ポートのデータ型を設計値として定める`
- 境界: 見出しや導入文から Module 設計が主体だと一意に定まる間は主語を省略する。主体が変わる箇所では、`実験実施者が結果を実験記録へ残す` のように新しい主体と責務を明示する
- 境界: 実行時に動作するソフトウェアや機器、静的な制約を保証する仕様、IF、型、プロトコルは主体にしてよい

## 実行情報

### 手順とコード例

- Bad: コマンド列だけを示し、必要な権限、成功の確認方法、失敗後の状態を示さない
- Good: 開始条件、操作、期待結果、確認方法、安全な再試行または回復方法を示す
- Bad: `...` や未定義の変数を含む断片を「そのまま実行できる例」と呼ぶ
- Good: 実行に必要な完全な例を示すか、「説明用断片」と明示する
- 境界: 回復手段が存在しない操作では、架空の回復手順を作らず、不可逆性を操作前に示す

### 擬似コード

- Bad: 設計文書へ実装のクラス、関数、条件分岐、呼出順を擬似コードとして複製する
- Good: 責務、境界、依存関係、データまたは制御の流れを文章、表、図で示し、具体的な実装が必要なときは実コードを参照する
- 許容: API や DSL の利用者へ呼出方法を示す擬似コード。擬似コードであることと実コードとの差を明示する
- 禁止: アルゴリズム仕様であっても、設計・アーキテクチャ文書で実装の分岐や処理順を模写する擬似コード

## 英語

- Bad: 事実が明らかな箇所の `This data may suggest that...`
- Good: `This data shows...`
- Bad: 推測にすぎない因果を `X causes Y` と断定する
- Good: 根拠の強度に応じて `X may cause Y` と限定する
- 境界: 事実には不要な hedging を用いず、推測は推測として弱める。受動態を多用しない
