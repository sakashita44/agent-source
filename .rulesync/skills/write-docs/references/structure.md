# 文書構造

見出し、リスト、情報の順序、構成案を設計するときに適用する。

## 見出しとリストの粒度

見出しとリストの階層は、要素間の対等、包含、依存の関係を読者へ伝える。同一階層の項目は、対等で独立した関係として読まれる。

- 対等性: 「X の理解に Y が必要か」「X は Y の枠組みの中でのみ意味をなすか」を問い、該当する X を Y の下位に置く。互いに独立し、包含関係にない要素だけを同一階層に置く
- 近接配置: 読者が関連づけて理解する必要がある項目を隣接させる
- 横断的内容: 複数要素にまたがる内容を、いずれか一要素の配下に置かず、関係する要素と同一階層へ独立させる
- 全体像の先置: 本文冒頭に、参照場面、要素間の関係、スコープを含む全体像を置く。以降の節を、その内訳として読める順序にする
- 構成の反復: 対等な要素の内部構成を揃える。特定の要素にだけ補足が必要な場合や、他の要素には該当する内容がない場合は、対象の性質に基づく逸脱として足し引きしてよい
- 分類と例示: 分類軸と分類項目を複数の対象へ適用できる基準として定義する。具体例を、概念、規則、分類項目の下位に置く
- 文脈外識別可能性: 見出し、リンクラベル、図表名は、目次、検索結果、リンク一覧から単独で読んでも対象と役割を識別できる名称にする

次のいずれかに該当する場合、粒度を見直す。

- 同一階層の項目が 3 個以上並ぶ。5 個以上は原則として中間ノードで束ねる
- ある項目の理解に、別の項目の理解を前提として必要とする
- 項目間で抽象度が揃っていない
- 複数要素にまたがる内容が、特定の一項目の配下にある
- 対等な要素の下位構成が、対象の性質による理由なく異なる
- 具体例が、概念、規則、分類軸と同一階層にある
- 見出しやラベルが「詳細」「その他」「こちら」だけで対象を識別できない

同種の語を列挙する用語定義、チェック項目、選択肢は、項目数が多くても分割を要さない。異なる観点や工程が並ぶ場合だけを判断対象とする。

見出しは 5 段まで用いてよい。タイトルを第 1 段、主要な節を第 2 段と数える。階層を浅くするために包含・依存関係にある要素を同一階層へ上げない。

## 構成案による確認

新規作成と全体改稿では、本文を書く前に階層構成を確定させる。

### 構成案を組む

構成案を YAML で一時ファイルへ書き出す。各ノードに同じキーを定義する。対等な要素は、個別の下位構成を持たず、`schemas` の共通構成を参照する。

```yaml
title: ドキュメントの題
overview:
  対象: 文書が説明する対象
  想定読者: 主な読者とその立場
  参照場面: 読者がこの文書を開く状況
  読者の目的: 文書から得る判断または実行する行動
  要素間の関係: 本文が扱う要素と、その間の関係
  スコープ: 扱う範囲

schemas:
  <共通構成の名前>:
    - <子見出し 1>
    - <子見出し 2>

sections:
  - heading: 見出し文字列
    role: この節が答える問い
    depends_on: [前提として理解が必要な他ノードの heading]
    schema: <共通構成の名前>   # children と排他
  - heading: 見出し文字列
    role: この節が答える問い
    children:
      - heading: 子見出し
        role: この節が答える問い
```

共通構成との差分は `schema_deviation` に記録する。

```yaml
schema_deviation:
  add: [<足す子見出し>]
  omit: [<省く子見出し>]
  reason: 差分が対象の性質から生じている理由
```

理由を書けない差分は、共通構成を直すか、その節を別の階層へ移す。

### 構成案を検査する

- 対象、想定読者、参照場面、読者の目的に対して、各節の内容と順序が対応しているか
- 一つの節に複数の読者目的が混在していないか
- 読者の行動に必要な情報を欠かず、寄与しない詳細を含んでいないか
- `depends_on` が兄弟を指す場合、依存先を上位へ移すか、依存するノードを依存先の `children` へ移したか
- 3 個以上の兄弟を束ねられないか。5 個以上に中間ノードがあるか
- `schema_deviation.reason` が対象の性質を示しているか
- 兄弟の `role` の抽象度が揃っているか
- 横断的内容が独立したノードにあるか
- `sections` が `overview` の内訳として読めるか
- 意味的に近いノードが隣接しているか
- 具体例が例示対象の下位にあるか
- 見出しが文脈外でも対象と役割を識別できるか

### 本文を書く

検査を通した構成案を骨格として本文を書く。構成を変える場合は構成案へ戻して検査し直す。構成案は作業用とし、成果物へ含めない。
