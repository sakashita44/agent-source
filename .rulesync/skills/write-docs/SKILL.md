# write-docs

技術ドキュメントを以下のルールに従って執筆・更新する。本ファイルと `references/` が Documentation Style の正本であり、verify-docs スキルはこのルールに照らして検証する。

## 利用方法

### 手順

1. 対象ファイルと関連ドキュメントを読み、説明対象、主な読者、読者の目的、正本、既存の構成・用語・トーン、文書内・文書間の導線を把握する
2. 新規作成・全体改稿では、本文を書く前に構成案を作り、`references/structure.md` に従って検査する
3. 文書の内容種別に応じて `references/content-types.md` を読み、該当する規則を適用する
4. 日本語を書くときは `references/japanese-style.md` を読み、文体と表現を整える
5. 以下の普遍原則と、読み込んだ参照ファイルの規則に従って執筆する
6. 複数ファイルにわたる改稿や大規模な新規執筆では、完了後に verify-docs での検証を提案する

構成案の作成は、新規作成と章立ての組み替えを伴う改稿に限る。段落単位の修正、語句の直し、追記では、構成案を経ずに直接編集する。

### 参照先

- `references/structure.md`: 見出し、リスト、情報の順序、構成案を設計するときに読む
- `references/content-types.md`: README、手順、コード例、Reference、設計・アーキテクチャ文書を書くときに読む
- `references/japanese-style.md`: 日本語の本文、見出し、リスト、指示を書くときに読む
- `references/review-examples.md`: 規則の適用可否に迷ったとき、またはレビューで違反を説明するときに読む。通常の執筆では読まない

### 適用範囲

Markdown ドキュメント、PR description、doc comment、ADR に適用する。コミットメッセージの書式は commit スキルの規則に従う。常体と事実の断定は共通する。

## 読者中心の原則

### 文書の目的

文書の内容は、ファイル名や既存の章立てではなく、説明対象、主な読者、読者の目的によって決める。

- 主な読者: その文書を最初に必要とする読者を定める。利用者、導入者、設計者、運用者、保守担当者など、立場によって必要な情報を区別する
- 読者の目的: 読者が文書を開く状況と、読後に判断または実行する行動を定める
- 目的の分離: 一つの文書または節には、一つの読者目的を割り当てる。異なる目的の詳細を混在させず、目的別の文書または節へ分離する
- 必要十分性: 読者の行動に必要な前提、判断材料、実行情報、完了条件を欠かさず、行動に寄与しない詳細を置かない
- 入口文書の責務: README などの入口文書は、主な読者が最初の行動へ進むために必要な情報を順に置き、異なる目的の詳細へ案内する

### 読者からの独立性

#### Zero-Context Reader Principle

成果物は、想定読者に対して自己完結させる。想定読者に一般的な分野知識を求めてもよいが、文書外の経緯やプロジェクト固有の暗黙知を要求しない。現在の事実を書き、経緯の物語や変更履歴を書かない。

- コミットメッセージと PR タイトル: diff が対象であるため、時制的な記述を許容する
- README と doc comment: 現在の構成と挙動を書く。移行の経緯は CHANGELOG とコミットログに記録する
- 文脈外識別可能性: 見出し、リンクラベル、図表名、参照名は、目次、検索結果、リンク一覧など本文外に現れても対象と役割を識別できる名称にする

#### 時間的コンテキストからの独立

現行仕様を説明する文書は、執筆時点や過去版の知識に依存させず、現行状態を直接記述する。「現在」「現時点」「新しい」「最新」「従来」「今後」「まだ」など、基準時点が不明なまま意味や正確さが変わる表現を用いない。

- 比較が必要な場合は、版、日付、方式名、適用期間などの基準を明記する
- 未提供の機能、予定、予測は、現行仕様から将来計画を扱う文書へ分離する
- CHANGELOG、リリースノート、ADR、移行手順、障害報告、将来計画では変化や時点を記録してよい。日付、バージョン、移行元、移行先などの基準点を示す

### 読者の導線

文書内と文書間の導線は、読者が目的に応じて次に読む場所と取る行動を判断できるように構成する。

- 文書内: 概要、見出し、本文の順序、節への参照によって、目的に必要な節へ到達できるようにする。本文の順序と包含関係だけで到達できる節への参照を重ねない
- 文書間: トップレベルの README など、想定読者が最初に読む文書から目的別の関連文書へ到達できるようにする。独立した入口を除き、意味的に独立した情報には、先に読む場所からの導線を置く
- 参照条件: 別文書や同一文書内の節へ案内するときは、その情報が必要になる条件と参照先を示す
- 位置に依存しない参照: 「上記」「下記」「左図」「次節」など位置や外観だけで対象を示さず、見出し名、図表名、項目名を名指す
- 正本と局所要約: 複数文書で再利用する規則、仕様、定義には正本を一つ定める。他の文書には、その場の判断または行動に必要な局所要約と、必要になる条件を伴う正本への参照だけを置く

## 構造と表現

### 情報の構造

- 階層の意味: 同一階層には対等で独立した要素を置き、包含または依存する要素を下位に置く
- 情報の順序: 全体像を先に置き、前提から依存情報へ進む。意味的に近い情報を近接させ、複数要素にまたがる内容を独立させる
- 構成の反復: 対等な要素には共通の内部構成を用いる。対象の性質による差だけを足し引きする
- 分類と例示: 分類軸と分類項目を複数の対象へ反復できる基準として定義し、具体例を例示対象の下位に置く
- 識別可能な名称: 見出しとラベルには、その要素の役割または答える問いを表す短い名称を付ける

詳細な判断基準、見出し数、階層の深さ、構成案の形式は `references/structure.md` に定める。

### 表現の原則

- 簡潔性: 冗長・重複な言い回しを避け、各論点を一度だけ平明に述べる
- 用語の一貫性: 同じ概念には同じ用語を使い、異なる概念を同じ用語で括らない。別名が必要な場合は初出時に対応を定義する
- メタ言及の禁止: 「本節では説明する」など文書自体を語らず、内容を直接述べる
- 強調は構造で: 重要性を見出し、リスト、インラインコード、文の順序で表す。地の文中の太字とイタリックによる強調を用いない。既存文書の太字ラベルは許容するが、新規記述では太字なしのコロン形式を既定とする
- 演出の禁止: 中身のない強調語、空虚なメタ動詞、定型の枕、煽り、決め台詞を用いない
- 効能約束の禁止: 読者の利得を約束せず、読者が設定していないゴールを前提とせず、事実を提示する

日本語では常体を用い、`references/japanese-style.md` の動詞、主体、指示、表記の規則を適用する。

英語では、動詞と助動詞の強度を主張内容に合わせる。事実には不要な `may`、`might`、`could`、`seems`、`tends to` を用いず、推測は根拠の強度に応じて限定する。受動態を多用しない。

### 禁止パターン

- 確定ラベル: 決定済みの事実へ `（確定）`、`[Fixed]`、`[Decided]` などを付けない。未解決を示す `TODO`、`FIXME`、`（検討中）` は許容する
- 連番見出し: 見出しへ `1.`、`1.1` などの番号を付けない
- diff 記述: README や設計文書へ「X から Y に変更」「以前は Z を使用」などの変更履歴を書かない
- 対比による説明: 読者が棄却案を知らなくても意味が通る場合は、「A ではなく B」と書かず、採用した B を直接記述する
- 不在の宣言: 読者が存在を当然期待する場合を除き、「X には言及しない」など対象外を宣言しない。期待される場合は、不在の理由と記録先を示す
- メタラベル見出し: 裸の概念名、対象の列挙、分類・進捗・対象限定を示すカッコ書きを見出しに置かない
- 実装模写の擬似コード: 設計・アーキテクチャ文書で、実装の型、関数、分岐、処理順を擬似コードとして模写しない。擬似コードは、ツール、API、DSL、フレームワークなどの利用者向け利用例に限って用いる

禁止パターンの Good、Bad、適用境界は `references/review-examples.md` に示す。

## 完了確認

執筆後、対象ファイルと変更した導線を通読する。

- 主な読者と読後の行動を特定できるか
- 一つの文書または節に、異なる読者目的が混在していないか
- 行動に必要な情報を欠かず、目的に寄与しない詳細を含んでいないか
- 現在の事実、将来計画、変更履歴が、それぞれ適切な文書にあるか
- 正本が一つに定まり、他の文書の局所要約がその場の判断に必要な範囲へ収まっているか
- 見出し、リンク、図表、参照対象を文脈外でも識別できるか
- 手順、コード例、Reference、設計文書に、内容種別ごとの必須情報があるか
- 同じ概念に同じ用語を用い、文の主体と関係を具体的に記述しているか
- リンク先、コマンド、コード例、期待結果を可能な範囲で検証したか
