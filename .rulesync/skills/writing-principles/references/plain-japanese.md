# 平易な書き言葉の例

「日本語の文体」に定める平易さの判断に迷う場合に参照する例を示す。例は判断の方向を示すものであり、置き換えの一覧ではない。判断の軸は、表現の硬さや柔らかさではなく、想定読者が一義に解釈できるかどうかである。

## 口語や俗語を改める例

| 口語や俗語 | 改めた表現 | 理由 |
| --- | --- | --- |
| 小さな窓が出る | ダイアログが表示される | UI 上の正式な名称を用いる |
| 設定ファイルをデータファイルの隣に置く | 設定ファイルをデータファイルと同じフォルダに配置する | 位置関係の基準と範囲を一義に示す |
| 値が跳ぶ | 値が不連続に変化する | 現象を技術用語で示す |
| ざっくり確認する | 主要な項目に絞って確認する | 範囲を示す |
| いい感じに揃える | 命名規則に従う | 基準を示し、遵守を求める強度を明確にする |

## 硬くても維持する例

| 維持する表現 | 避ける言い換え | 理由 |
| --- | --- | --- |
| 該当するグループのマーカを選択する | そのグループのマーカを選ぶ | 「該当」は指示対象を条件で特定し、「その」より解釈の幅が狭い |
| 座標の補間は行わない | 埋めない | 処理の名称を示す |
| 当該ファイルを削除する | そのファイルを消す | 「当該」は直前に示した対象に限定する。「消す」は削除と非表示を区別できない |
| 以下の条件を満たす場合に限り実行する | こういう時だけやる | 条件の範囲を明示する |
| 設定を反映する | 設定を効かせる | 処理の名称として確立している |

## 硬くても曖昧なので改める例

一義に解釈できない表現は改める。硬い表現であることは、維持する理由にならない。

| 曖昧な表現 | 改めた表現 | 理由 |
| --- | --- | --- |
| 適宜、設定を更新する | 依存関係を追加したときに、設定を更新する | 「適宜」は実行の条件を示さない |
| 基本的に再実行する | 失敗した場合は再実行する。ただし `<例外>` は除く | 「基本的に」は例外の有無を示さない |
| ログ等を確認する | ログとスタックトレースを確認する | 「等」は範囲が読者によって変わる |

## 汎用の和語動詞を改める例

技術文書では、関係を特定する漢語の動詞を選ぶ。「置く」「書く」「使う」「出る」は、配置、定義、利用、出力のどの関係かを特定しない。同じ漢語の中でも、関係に合う語を選ぶ。

| 汎用の和語動詞 | 改めた表現 | 理由 |
| --- | --- | --- |
| サービスの構成を `container/` に置く | サービスの構成を `container/` に配置する | 配置の関係を示す |
| 記録対象を `observations.toml` に書く | 記録対象を `observations.toml` に定義する | ファイルの内容が対象を定めることを示す。「記述する」は文章やコードを書く行為を指す |
| 登録に CLI を使わない | 登録に CLI を用いない | 書き言葉の動詞を用いる |
| journal に理由が出る | journal に理由が出力される | 出力の主体と結果を示す |
| 以降の操作は root shell で行う | 以降の操作は root shell で実行する | 処理の名称を示す |
| 原因を調べる | 原因を調査する | 処理の名称を示す |

「書き出す」「置き換える」「取り消す」など、技術用語として確立した和語は改めない。文章を書く行為そのものを指す「書く」も改めない。

## 用語に選ばない語の例

辞書にある語でも、想定読者の分野で一般的でない訳語や、他分野の専門用語は用語にしない。識別子で直接示せる対象には別名を設けない。

| 避ける用語 | 改めた表現 | 理由 |
| --- | --- | --- |
| 変更前の基線を確定する | 変更前の状態を記録し、比較の基準とする | 「基線」は baseline の訳語で、構成管理の外では通じにくい |
| 宣言ファイルに記録対象を宣言する | `observations.toml` に記録対象を定義する | 「宣言」はプログラミング由来の語で、運用者の操作が伝わらない。ファイル名で直接示せる |

## 情報の所在を表す例

「正本」は、編集する場所、生成元、規則を定める文書、記録先、優先する情報源のどれを指すかを特定しない。関係に応じた動詞で記述する。

| 関係 | 表現 |
| --- | --- |
| 編集する場所 | X で管理する |
| 生成元 | X から生成する。名詞が必要な箇所では「生成元」 |
| 規則を定める文書 | 規則を X に定める。名詞が必要な箇所では「規定元」 |
| 記録先 | X へ記録する |
| 食い違い時に優先する情報源 | 食い違う場合は X を優先する |
| 同じ内容を複数箇所に記載しない要求 | 一元管理する、二重管理しない |

正式な原本の意味で「正本」を用いる場合は、その意味が文脈から判別できるように記述する。

## 業界で使われる口語的な語の例

使われている頻度ではなく、別の解釈の余地があるかで判断する。

| 表現 | 判断 | 理由 |
| --- | --- | --- |
| テストが落ちる | 「失敗する」に改める | 異常終了とアサーションの失敗を区別できない |
| API を叩く | 「呼び出す」に改める | 動作の対象を一義に示す |
| CI を回す | 「実行する」に改める | 反復の含意があり、一回の実行と区別できない |

## 利用者の語彙や表現を採用しない例

利用者の発話は、発話の文脈を前提とした口語であることが多い。成果物の読者はその文脈を持たないため、意味を保ったまま、書き言葉と正確な用語へ改める。

| 利用者の入力 | 成果物での表現 | 理由 |
| --- | --- | --- |
| ユーザーが使った語彙を安易に採用しない | ユーザーが提示した語彙や表現を安易に採用しない | 規則の対象は発話の動作ではなく、成果物へ持ち込む語彙と表現である。「語彙」のみでは言い回しを含まない |
| あのファイルを直して | `<パス>` を修正する | 指示語は発話の文脈に依存する |
| ログがおかしい | ログに `<具体的な事象>` が出力されている | 評価語は事象を示さない |
| 課題 / チケット / Issue を混在させる | 「Issue」に統一する | 別の対象と解釈される可能性がある |
