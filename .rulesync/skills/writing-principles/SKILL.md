# Writing Principles

## 読者と内容

主な読者、文章を読む状況、読後に必要な判断または行動を定める。これらは内容と構成の決定に用い、本文への記載は文書の利用に必要な場合に限る。読者の行動に必要な前提、判断材料、実行情報、完了条件を漏れなく示し、目的に寄与しない詳細は置かない。

原則として一つの文書または節には一つの読者目的を割り当て、異なる目的の詳細は別の文書または節へ分ける。

想定読者に向けて文章を自己完結させる。一般的な分野知識は前提としてよいが、文章外の経緯やプロジェクト固有の暗黙知は前提としない。

他の成果物と併読される文章では、併読対象から得られる事実の重複を避け、その文章で示すべき意図、理由、判断条件を補う。

見出しには、文書タイトルや上位見出しを踏まえ、兄弟節との違いと役割が分かる簡潔な名称を用いる。リンクラベルや参照名には、リンク一覧や参照元から対象と役割を識別できる名称を付ける。

操作を指示する文章には、開始条件、対象と判断条件を伴う操作、期待される結果と確認方法を置く。失敗する可能性がある場合は、安全な再試行や復元方法、または回復不能である旨を操作前に示す。

README には、リポジトリの責務として自然な範囲の前提、設定、操作、診断情報を置く。前提となる外部環境は、リポジトリ固有の条件を示す範囲で扱う。

通常手順には、完成状態で反復する定常的な手順を置く。移行、初期構築、診断、隔離検証などの条件付き操作は、補助手順または専用の成果物に置く。

## 構造と導線

同一階層には対等かつ独立した要素を置き、包含または依存する要素は下位に置く。説明は全体像と前提から詳細へと進め、意味的に近い情報を近接させる。横断的な内容は特定の要素配下に押し込めず、対等な要素には共通の内部構成を用いる。具体例は例示対象の下位に置く。

一つの段落には一つの論点を置き、段落の冒頭でその論点や前段との関係を把握できるようにする。

読者が入口から目的に必要な情報や次の行動へ到達できる導線を置く。意味的に独立した情報を別文書へ分ける場合は、参照が必要となる条件と参照先を示す。

## 分量の配分

主題の重要度に応じて説明の分量を配分する。主張を先に示し、成立条件、例外、実装上の詳細は補足として格下げする。

節や段落の分量を、重要度にかかわらず一律に揃えない。構造上の対応と分量の対称性を区別し、対等な位置にある要素へ同じ長さの説明を機械的に割り当てない。

削除しても読者の理解、判断、行動に影響しない紹介、言い換え、前提の再掲、書き手がそう定めた経緯や理由は置かない。読者の判断に影響しない細かな懸念も網羅的に列挙しない。提出前に、節、段落、一文ごとに読者の目的に必要かを問い直す。

## 時間と事実

現在の事実、変更履歴、将来の計画を分離し、現行状態を説明する文書に変更履歴を混在させない。現行状態を説明する文章では、執筆時点に依存する「現在」「最新」「従来」「今後」などの表現を避ける。PR、Issue、ADR、障害報告などで時系列が必要な場合は、日付、版、変更元、変更先などの基準を示す。

根拠が示す範囲を超えて主張を一般化しない。因果関係を述べる場合は、観測された相関と明確に区別し、確認できる作用機序または根拠を示す。

## 執筆状態

文書の内容を、執筆途中であることを理由に変形しない。確定している内容は本文に維持し、未解決の事項のみを、対象と必要な判断が分かる具体的な `TODO:` として局所化する。

確定した仕様、設計、責務、適用範囲は、未整備な実装や運用の状態に合わせて表現を弱めたり、暫定的な表現に変えたりしない。実装やドキュメントが未整備であっても方針自体が確定している場合は、未整備な点への対応を `TODO:`、Issue、将来計画など適切な成果物へ分離する。

未決定の値や方式を、完成形を装って本文に補わない。`TODO:` と本文が矛盾する疑いがあり、規則を定める文書や確認可能な事実から解消できない場合は、一方を推測で書き換えず、必要な判断を `TODO:` として示す。

## 日本語の文体

常体で書き、確認できた事実を明確に述べる。ですます調や敬語は用いない。

確認できた事実を「〜と思われる」「〜と考えられる」と曖昧に表現しない。観察、所見、一次情報に基づかない推論を述べる場合は、その確度が読者に正しく伝わる表現にする。判定基準とするのは文末の語形ではなく、記述内容の確度である。

常体は「だ」「である」の画一的な反復ではない。文の役割に応じて、動詞による終止、体言止め、「〜のこと」「〜すること」を使い分ける。

- 体言止め: 見出し、リスト項目、表のセル、要点の提示など、述語を補わなくても関係と意味が確定する場合に用いる。連続する本文を体言止めだけで構成し、主体や関係を曖昧にしない
- 指示の終止形: 読者へ短い行為を求める文は、「参照のこと」「確認のこと」など動作名詞に「のこと」を続けた形を既定とする。目的語、条件、方法を伴って不自然になる場合は「〜すること」を用いる。事実の説明や通常の手順は動詞で終止する
- 規範の強度: 義務と推奨を区別する場合は、義務を「必ず〜のこと」、推奨を「〜を推奨する」など、読者がその強度を明確に判別できる形にする
- コピュラ: 「XはYである」は定義、同定、分類、判断に用いる。動作、配置、責務、条件を「〜である」で終止しない

## 主体と動詞

選択、決定、記録、実行、保証を実際に担う主体を識別できるように書く。

- 意味上の主体: その行為を担う人、役割、ソフトウェア、機器、仕様を特定する。意味上の主体の特定と、文法上の主語の明示は区別して判断する
- 主語の明示: 見出し、導入文、直前の文から主体が一意に定まる場合は主語を省略してよい。主体が変わる箇所、責務の境界、複数の解釈が生じる箇所に限って明示し、同じ主体名を各文に機械的に繰り返さない
- 設計判断: 設計値、規則、採用対象を「選ぶ」「定める」「決める」主体は担当者または役割である。成果物を擬人化して判断の主体とせず、決定した値や事実を「記録する」先として書く
- 実行時の動作: 実際に処理を行うソフトウェアや機器を主体にしてよい。システムの処理によって結果が定まる場合は「選ばれる」「決まる」「実行される」と書き、行為者の識別が必要な受動文では行為者も明記する
- 静的保証: 仕様、インターフェース、型、プロトコルが制約や性質を保証する場合は、それらを主体にしてよい
- 関係を表す動詞: 規則には「定める」、配置には「置く」「収める」、記録先には「記録する」、責務には「担う」、内部構造には「含む」「ある」を用いる。「持つ」「扱う」だけで異なる関係を大雑把に括らない
- 情報の所在: 「正本」を、編集する場所、生成元、規則を定める文書、記録先、食い違い時に優先する情報源の総称として使わない。関係に応じて「Xで管理する」「Xから生成する」「規則をXに定める」「Xへ記録する」「食い違う場合はXを優先する」と動詞で書き、ラベルなど名詞が必要な箇所では「規定元」「生成元」を用いる。同じ内容を複数箇所に置かない要求は「一元管理する」「二重管理しない」と直接書く。「SSOT」「信頼できる唯一の情報源」へ機械的に置き換えない。正式な原本の意味で「正本」を用いる場合は、その意味が文脈から判別できるように書く

## 形式の選択

同じ形式を全体へ一律に適用しない。全体を地の文のみ、箇条書きのみ、あるいは `ラベル: 値` の形式のみで構成すると、読者が構造から意味を読み取りにくくなる。

内容の性質に合わせて形式を選択する。列挙できる並列の要素には箇条書き、判断の流れと理由には文章、対応関係には表またはラベルを用いる。

宣言文が値の提示にとどまる場合はラベル化を検討する。「XはYである」と述べるだけの文は `X: Y` へ置き換えやすい。ただし、置き換えによって理由や条件が失われる場合は文のまま残す。

## 表現

- 各論点を必要十分な長さで一度だけ述べる
- 同じ概念にはできる限り同じ用語を用いる。文脈上、別の語で言い換えたほうが自然に読める場合は言い換えてよいが、読者が別の対象と誤解しない範囲にとどめ、定義した用語、識別子、UI 上の表記は言い換えない
- 用語を揃える際、既存の用語との整合だけを理由に語を選ばない。既存の用語が不自然または意味の取りにくい語であれば、既存用語側を改め、同じ用語を使うすべての箇所を一括して変更する
- 一般に通じない造語、略称、独自ラベルを用語にしない。区別が必要な場合は、「説明用のコード例」「実行可能なコード例」のように一般語に修飾を加えて表す
- 「本節では説明する」など、構成や説明行為のみを予告する形式的なメタ言及を避け、内容を直接述べる。文書の目的、対象範囲、規定する内容、規定元、他文書との境界を示す記述はこの限りではない
- 「空虚な」「適切な」など、判定の基準を読者が特定できない評価語だけで規則を書かない。具体例または判定基準を添える
- 「非常に」「極めて」など情報を加えない強調語、誇張表現、定型の前置き、読者が求めていない効能の約束を避ける
- 読者が棄却案を知らなくても意味が通じる場合は、不要な「AではなくB」型の対比を避け、採用した内容を直接述べる
- 不在や対象外は、読者がその存在を当然期待する場合に限って明記し、理由と記録先を示す
- 「上記」「下記」「次節」など位置関係のみで対象を示さず、見出し名、図表名、項目名を明確に指定する
- リスト項目冒頭のラベルは、太字にせず `用語: 説明` の形式を用いる
- 決定済みの事実に `（確定）` や `[Fixed]` などの状態ラベルを付けない
- 見出しに機械的な連番を付けない
- 重要性は見出し、リスト、インラインコード、文の順序で表し、地の文における太字や斜体に頼らない
- 句読点、英数字、用語の表記は、対象リポジトリの既存の規則に揃える
- 英語では主張に不要な hedging を避け、受動態を多用しない

CLI や UI の実行時メッセージには、製品の対話様式に応じた自然な文体を用いる。日本語文書向けの常体を機械的に適用せず、日本語では必要に応じて丁寧体を用いてよい。英語を用いる場合は、同一インターフェース内で表記とトーンを揃える。

通常の会話には、その目的に合った文体を用いる。成果物固有の構造と書式は、対象の成果物を扱う Skill に従う。

## 推敲

書き上げた文書を読み直し、平易で自然なビジネス文書の日本語に整える。追記や部分修正を重ねた文書では、追記箇所単体にとどまらず前後の文脈とあわせて確認する。

- 文のつながり: 追記した文は、前後の文と一続きで読めるように整える。後付けの理由、断り書き、段落末尾への一文追加で済ませず、必要であれば段落内の論理的な位置へ移し、前後の文とあわせて書き直す
- 語調: 弁明、予防線、念押しの調子を避け、決定事項や事実を直接述べる
- 形式: 内容の性質と形式が合っていない箇所は、「形式の選択」に従って文章、箇条書き、表、ラベルを切り替える。判断の流れや理由が箇条書きに分断されている箇所は文章にまとめ、文の中に並列要素や対応関係が埋もれている箇所は箇条書きや表に書き出す
- 意味の保持: 推敲では意味、事実関係、規範の強度、コード、コマンド、識別子を変更しない。意味を変えなければ修正できない箇所は、手を加えず問題点として報告する
- 用語の変更: 推敲で用語を改めた場合は、推敲の対象範囲外も含め、同じ用語を用いる全箇所を一括して改める
