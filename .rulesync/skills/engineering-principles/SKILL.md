# Engineering Principles

## 実装手段の判断ラダー

要求を満たす手段は次の順に検討し、最初に成立した段階で確定する。下位の段階は、上位の段階が成立しない理由を説明できる場合に限り選択する。

1. 作る必要があるか。確認された要求で必要性を説明できないものは作成しない
2. このコードベースに既にあるか。既存の実装、構造、規約で満たせるなら再実装しない
3. 言語の標準ライブラリで対応できるか
4. 実行基盤またはプラットフォームの機能で対応できるか
5. 既に導入している依存関係で対応できるか
6. 数行で記述できるか。その範囲で収まるなら新たな依存関係を追加しない
7. 要求を満たす最小限のコードを実装する

7段階目が、検証、識別子生成、日付処理、UI パターンなど、確立した解のある問題の再実装になる場合は、十分に保守されたライブラリの導入を先に検討する。

## 判断原則

- YAGNI に従い、確認された要求を満たす最小限かつ十分な解決策を選ぶ。将来の可能性だけを理由に機能や拡張点を増やさない
- 要求を満たすために必要な複雑さだけを導入する。必要性を要求、失敗形態、測定結果で説明できない抽象化、拡張点、設定、互換層、最適化は追加しない
- 小さな判断では既存の命名、構造、型付け、依存関係の規約を優先する
- 重要な基盤には確立した標準を用い、ドメイン固有の問題には目的に合わせた設計を行う
- 個別の症状ごとに例外や分岐を積み重ねず、共通する原因を解消して責務境界を整理する
- 性能最適化は観測した制約と測定結果に基づいて行い、予測だけで複雑さを増やさない
- 目的とエコシステムに適した言語を選ぶ。例えば JavaScript が候補に挙がる場合は、固有の理由がない限り、より堅牢な TypeScript を用いる

## 検討量の配分

対象の重要度に応じて、検討量、設計の複雑さ、説明の分量を配分する。すべての対象に対して一律の密度で設計判断を適用しない。

ドメインの中核に設計判断を集中させ、周辺の定型処理は既存の規約と最短の手段で済ませる。中核と周辺で、抽象の数、分岐の扱い、テストの厚みが同等になっている状態は、配分が適切でない兆候である。

読み手や利用者の判断・行動を変えない懸念事項は、網羅的に列挙しない。提出前に、追加した機能、抽象、設定、分岐のそれぞれについて、要求に基づいて必要性を説明できるかを再確認する。

## 既存構造の扱い

変更前に対象ファイルと関連モジュールを精読し、責務、依存関係、既存の規約を把握する。既存の構造が要求を安全に受け入れられない場合は、機能追加に先立つリファクタリングを提案する。

明確な規約がない領域では、要求に必要な最小限の範囲で一貫した方式を定める。

## コード品質

読み手が役割を推測できる名前を用い、関数とモジュールの責務を絞り込む。可能な範囲で厳密な型を用い、実質的な重複を排除する。将来の再利用を予測した抽象化は避け、実際に繰り返される概念だけを共通化する。

条件分岐は正常系の流れを追いやすく保つ。ガード節と早期 return が入れ子を減らして条件を明確にする場合は、それらを優先する。

エラーは、回復、意味の変換、文脈の付加、または利用者への説明ができる境界で処理する。処理に意味を付加できない場合は、元のエラーと原因を保持して伝播させる。空の catch や成功扱いによってエラーを握りつぶさない。

## 互換性

リポジトリの規則またはユーザーが明示的に求めない限り、後方互換性を設計条件に含めない。互換性を維持しない変更では、移行用の分岐や旧形式の受け入れ処理を残さず、要求に最も適合する単純な完成状態へ置き換える。

互換性を維持する場合は、対象となる版、時点、契約、データ、利用者、期限を特定する。設計・実装の途中における一時的な状態や、利用実績のない挙動を互換性の対象に含めない。
