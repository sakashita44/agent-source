# レポート執筆ガイドライン

## 構成

承認済みプランのアウトラインを起点に、findings に合わせて更新した構成で書く。標準形:

```markdown
# <タイトル>

<調査目的と手法の要約 2〜3 行。調査日を明記 (Web 情報は陳腐化するため)>

## エグゼクティブサマリ

<主要な結論を 3〜7 個の箇条書きで先出し。各項目に確度を添える>

## <本文セクション> (複数)

<notes の事実に基づき執筆。構成は「問いへの答え → 根拠 → 留保」の順>

## 結論と示唆

<サブ質問への回答を統合し、依頼の目的 (判断・行動) に引き付けて述べる>

## 未解決の論点

<調査で答えが出なかったこと、ソースが割れたこと、追加調査の提案>

## Sources

<参照した全ソースのリスト>
```

## 執筆手順

1. notes 全体を読み、アウトラインを更新する。findings が薄いセクションは統合し、想定外の発見があれば新設する
2. セクションごとに執筆する。1 セクション書くごとに対応する notes を参照し直す。記憶で書かない
3. 全セクション完成後に通し読みし、セクション間の重複・矛盾・用語の揺れを直す

## 引用のルール

- 本文の事実主張には出典参照を付ける。形式は脚注 `[^1]` または文中リンクのどちらかに統一する
- 数値・日付・固有の主張は必ず出典付き。一般論・自明な背景説明には不要
- ソースが矛盾している場合は両論を書き、どちらが有力かの判断と理由を添える
- 単発ソースにしか見られない主張は「(確度: low、単一ソース)」のように明記する
- Sources には URL、タイトル、参照日を書く

## 品質チェックリスト (提出前に自己検査)

- 事実の正確性: 本文の主張は notes の記録と一致しているか。notes にないことを書いていないか
- 引用の正確性: 出典はその主張を実際に支持しているか (関連するだけの URL を貼っていないか)
- 網羅性: 承認済みプランのサブ質問すべてに回答したか。できなかったものは「未解決の論点」に書いたか
- ソース品質: 主要な結論が一次情報に支えられているか。SEO 記事だけが根拠の結論はないか
- 分量と言語: ユーザの指定に合っているか
- 機械検証: `scripts/check_report.sh` (bash) または `scripts/check_report.ps1` (PowerShell) が RESULT: PASS を返しているか。FAIL のまま完成報告をしない
