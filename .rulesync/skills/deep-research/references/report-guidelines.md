# レポート執筆ガイドライン

## 構成

承認済みプランのアウトラインを起点に、findings に合わせて更新した構成で執筆する。標準形:

```markdown
# <タイトル>

<調査目的と手法の要約 2〜3 行。調査日を明記 (Web 情報は陳腐化するため)>

## エグゼクティブサマリ

<主要な結論を 3〜7 個の箇条書きで先出し。各項目に確度を添える>

## <本文セクション> (複数)

<notes の事実に基づき執筆。構成は「問いへの答え → 根拠 → 留保」の順>

## 結論と示唆

<サブ質問への回答を統合し、依頼の目的 (判断・行動) に引き付けて述べる>

## 未解決の論点

<調査で答えが出なかったこと、ソースが割れたこと、追加調査の提案>

## Sources

<参照した全ソースのリスト>
```

## 執筆手順

1. notes 全体を読み込み、アウトラインを更新する。findings が少ないセクションは統合し、想定外の発見があった場合は新設する
2. セクションごとに執筆する。1 セクション書くごとに、対応する notes を参照し直す。記憶に頼って書かない
3. 全セクション完成後に通読し、セクション間の重複・矛盾・用語や表記の不統一を修正する

## 引用のルール

- 本文の事実主張には出典参照を付与する。形式は脚注 `[^1]` または文中リンクのどちらかに統一する
- 脚注を用いる場合は、Sources に `[^1]: <URL> タイトル（参照日）` の形式で定義を置き、1 行に収めて URL を必ず含めること。箇条書きの `- [^1]: ...` も定義として受け付ける。本文や他のセクションに置いた定義は、検証スクリプトが Sources の定義として認識しない。コードブロックとインラインコード内の `[^...]` と URL は、脚注参照や文中引用として数えない
- 数値・日付・固有の主張には必ず出典を明記する。一般論や自明な背景説明には不要である
- ソースが矛盾している場合は両論を記載し、どちらが有力かの判断と理由を添える
- 単発ソースにしか見られない主張は「(確度: low、単一ソース)」のように明記する
- Sources には URL、タイトル、参照日を記載する

## 品質チェックリスト（提出前に自己検査）

- 事実の正確性: 本文の主張は notes の記録と一致しているか。notes にない内容を書いていないか
- 引用の正確性: 出典はその主張を実際に支持しているか（関連するだけの URL を掲載していないか）
- 網羅性: 承認済みプランのサブ質問すべてに回答したか。できなかった項目は「未解決の論点」に記載したか
- ソース品質: 主要な結論が一次情報に支えられているか。SEO 記事だけが根拠の結論になっていないか
- 台帳の裏付け: `sources.md` の各 URL が、実際に読んだソースとして `notes/` に記録されているか
- 分量と言語: ユーザーの指定に合っているか
- 機械検証: `scripts/check-report.mjs` が `RESULT: PASS` を返しているか。`FAIL` のまま完成報告をしないこと。`UNVERIFIED` の場合は、リンクの到達性が未検証であることを `progress.md` と報告に記載したか
