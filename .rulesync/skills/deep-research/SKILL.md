# deep-research

自然言語の調査依頼を「明確化 → プラン提案 (承認ゲート) → 反復深堀り → レポート生成」の 4 フェーズで処理する。全フェーズの状態をファイルに永続化する。調査は長時間・大量の読み込みを伴い、会話コンテキストは途中で圧縮・喪失され得るため、ファイルを唯一の真実源とし、どの時点で中断してもファイルから再開できるようにする。

このスキルは特定のツールやサブエージェント機構に依存しない。必要なのは Web 検索・Web ページ取得・ファイル読み書きだけであり、実行環境にある手段で行う。

## Phase 0: 準備

作業ディレクトリ `deep-research/<yyyymmdd>-<トピックのslug>/` をカレントディレクトリ配下 (ユーザ指定があればそこ) に作成する。

```text
deep-research/20260707-example-topic/
├── plan.md      # リサーチプラン (Phase 2 で作成、承認の記録も追記)
├── progress.md  # 進捗台帳 (Phase 3 の各ラウンドで追記。定量目標と現在地)
├── notes/       # サブ質問ごとの調査ノート (Phase 3 で蓄積)
├── sources.md   # 参照ソース台帳
└── report.md    # 最終レポート (Phase 4)
```

## Phase 1: 依頼の明確化

依頼が曖昧な場合のみ、最大 3 問の明確化質問をする。聞くべき典型は次の 3 点。

- 目的と読者: 何の判断・行動のための調査か。誰が読むか
- 範囲: 対象期間、地域、比較対象、除外事項
- 出力: レポートの言語、想定分量、重視する観点

依頼から自明なら質問せず Phase 2 に進む。質問のための質問はしない。

## Phase 2: リサーチプラン提案 (承認ゲート)

`references/plan-template.md` の形式で `plan.md` を作成し、内容を会話上でユーザに提示する。プランに必ず含めるもの:

1. **リサーチブリーフ**: 依頼を一段具体化した調査目的の言明
2. **サブ質問** (5〜10 個): 独立に調査可能で、合わせると目的を網羅する分解
3. **調査の深さと停止条件**: 反復ラウンド数、ソース数の目安
4. **レポートアウトライン (出力イメージ)**: 完成レポートの見出し構成と、各セクションに何が書かれる予定かの 1 行説明

規模はユーザの依頼の複雑さに比例させる。単純な事実確認寄りなら light、多面的なテーマや意思決定用途なら deep を提案する。

| 規模 | サブ質問 | ラウンド数 | 最低ラウンド | ソース数目安 | 最低ソース |
|---|---|---|---|---|---|
| light | 3〜5 | 1 | 1 | 5〜10 | 5 |
| standard | 5〜7 | 3 | 2 | 10〜30 | 10 |
| deep | 7〜10 | 5 | 4 | 30〜50 | 30 |

「最低ラウンド」「最低ソース」は目安ではなく下限であり、Phase 3 の停止判定と Phase 4 の入場ゲートで使う拘束値である。

提示後、ユーザの応答で分岐する:

- **承認** → `plan.md` に承認日時を追記し、`progress.md` を作成して (下記テンプレート) 最低ラウンド数・最低ソース数を転記してから Phase 3 へ
- **修正指示** → プランを修正して再提示 (回数制限なし)

```markdown
# 進捗台帳: <トピック>

- 拘束値: 最低 <N> ラウンド / 最低 <N> ソース (plan.md より転記)
- 掟: 各ラウンド開始時に plan.md とこのファイルを再読する。Phase 4 に入る前に
  SKILL.md 全文と references/report-guidelines.md を再読する。
  ラウンド間でユーザに方向性を質問しない (質問してよいのはプラン承認と早期終了承認のみ)

## ラウンド記録

### Round 1 (<yyyy-mm-dd hh:mm>)

- 対象サブ質問: <番号列挙>
- 実行クエリ数: <N> / 新規ソース: <N> 件 / 累計ユニークソース: <N> 件
- ギャップと次ラウンドの方針: <箇条書き>
```

掟をファイル側にも書くのは、長いセッションで会話コンテキストからスキル指示が消えても、ラウンドごとに必ず開くこのファイルが指示を再注入するためである。

承認前に本調査 (Phase 3) を開始しない。これはユーザが調査の方向とコストを制御するための唯一のゲートである。

## Phase 3: 反復調査ループ

承認済みプランのサブ質問を、ラウンド制で深堀りする。

**Phase 3 は自律実行する。ラウンド間でユーザに方向性・続行可否を質問しない。** 承認済みプランが方向性の契約であり、ラウンド内の判断 (どのクエリを打つか、どのソースを読むか、次に何を深堀るか) はすべてプランの範囲内で自分で下す。ユーザに質問してよいのはプラン承認 (Phase 2) と早期終了の承認 (後述) の 2 箇所だけ。例外は、調査の前提自体が崩れた場合 (トピックが実在しない、プランの中心仮定が誤りと判明した等) の中断報告のみ。

各ラウンドの手順:

0. **状態復元**: `plan.md` と `progress.md` を再読する。長いセッションではスキル指示や目標がコンテキストから消えている前提で、毎ラウンド必ず行う
1. **クエリ設計**: サブ質問ごとに表現・角度を変えた検索クエリを 2〜4 個作る。既知の learnings があるほど具体的なクエリにする (固有名詞、バージョン、年号を含める)
2. **検索と読解**: 検索結果から有望なソースを選んで読む。読んだ内容は原文を貼らず、`notes/<NN>-<サブ質問slug>.md` に「事実 + 出典 URL + 確度」の形式で要約して記録する。原文をコンテキストに溜めないことが長時間調査を成立させる
3. **ソース台帳更新**: `sources.md` に URL、タイトル、種別 (一次/二次/ブログ)、信頼性メモを追記する
4. **内省と記録 (ラウンド末)**: notes をプランと突き合わせ、次を明文化して `progress.md` にラウンド記録として追記する
    - 実行クエリ数、新規ソース数、累計ユニークソース数
    - 未回答・回答が薄いサブ質問 (ギャップ)
    - ソース間の矛盾 (両論を確度付きで記録し、どちらかを黙って採用しない)
    - ギャップを埋めるフォローアップ質問 (これが次ラウンドの調査対象)
5. **縮小**: 次ラウンドは対象質問数を約半分に絞り、残ラウンド数を 1 減らす。広く始めて深く絞る

停止条件:

- **通常終了**: プランの予定ラウンド数を消化した → そのまま Phase 4 へ
- **早期終了 (要ユーザ承認)**: 最低ラウンド数の消化後に限り、次のいずれかを理由に早期終了を提案できる。根拠 (数値) を `progress.md` に記録した上でユーザに承認を求め、承認されるまで Phase 4 に進まない
    - 飽和: 直近ラウンドの新規ソースが 2 件未満、かつ notes に新しい事実が追加されなかった
    - 全サブ質問に確度 high で回答済みで、かつ累計ソースが最低ソース数を超えている

最低ラウンド数を消化するまで、飽和を宣言してはならない。初期ラウンドの検索は同じ表層情報を返しがちで、深いソース (一次資料、原論文、実装コード) はフォローアップクエリで初めて到達することが多い。早い飽和判定はほぼ常に誤りである。

ソース品質の目安: 一次情報 (公式ドキュメント、原論文、原コード) > 専門メディア・査読記事 > 個人ブログ・SEO 記事。検索上位でも内容の薄いアグリゲータ記事は採用しない。重要な主張は 2 ソース以上で裏取りし、単発ソースの主張は確度 low と明記する。

サブエージェント (並列タスク委譲) が使える環境では、独立したサブ質問を並列に委譲して効率的に調査すること。委譲する場合、プロンプトに「答えるべき質問・notes への記録形式・出典と確度の明示」を含めて自己完結させ、結果は必ず notes ファイルに書かせる。

## Phase 4: レポート生成

**入場ゲート** (執筆を始める前に必ず行う):

1. この SKILL.md 全文と `references/report-guidelines.md` を再読する。ここまでで長大なセッションになっており、執筆ルールはコンテキストから消えているものとして扱う
2. `sources.md` の累計ユニークソース数が最低ソース数 (plan.md の拘束値) 以上であることを確認する。未達なら Phase 3 に戻る。残ラウンドがない場合は追加ラウンドの実施をユーザに提案する

執筆の要点:

1. アウトラインを実際の findings に合わせて更新する (計画時のアウトラインに固執しない)
2. セクションごとに notes を参照して執筆する。全セクション一括で書かない
3. 本文の主張には出典参照を付け、末尾に Sources 一覧を置く
4. 最後に全体を通し読みし、重複・矛盾・トーンの不一致を直す

**機械検証** (完了条件): 執筆後、同梱の検証スクリプトを実行し PASS するまで修正する。

```bash
# bash (Git Bash / Linux / macOS)
bash <このスキルのディレクトリ>/scripts/check_report.sh <作業dir>/report.md <最低ソース数>
```

```powershell
# PowerShell
& <このスキルのディレクトリ>/scripts/check_report.ps1 -Report <作業dir>/report.md -MinSources <最低ソース数>
```

検査内容: Sources セクションのユニーク URL 数 ≥ 最低ソース数、および本文各セクションに文中引用 (脚注 `[^n]` またはリンク) が 1 つ以上あること。スクリプトを実行できない環境では同じ項目を手動で検査し、結果を `progress.md` に記録する。FAIL のままユーザに完成報告をしない。

完成後、ユーザに報告する: report.md のパス、要旨 (3〜5 行)、確度の低い箇所と未解決の論点、機械検証の結果。

## 制約

- 承認前に Phase 3 を開始しない
- Phase 3 のラウンド間でユーザに方向性を質問しない。ユーザへの質問はプラン承認と早期終了承認の 2 箇所のみ
- 出典を示せない主張をレポートに書かない。推測は推測と明記する
- レポートの言語はユーザの依頼言語に合わせる (指定があればそれに従う)
- 途中で中断・再開する場合、まず作業ディレクトリのファイルを読んで状態を復元する
