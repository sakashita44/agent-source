# Deep Research

調査依頼は、明確化、プラン提案、反復調査、レポート生成の 4 段階で処理する。各段階の状態をファイルへ永続化し、どの時点で中断してもファイルから再開できるようにする。出典台帳は成果物の一部であり、会話内だけにとどめない。

Web 検索、Web ページの取得、ファイルの読み書きには、実行環境で利用できる手段を用いる。独立したサブ質問は、`subagent` に従って原則として委譲する。

## 作業ディレクトリ

`deep-research/<yyyymmdd>-<トピックのslug>/` を、実行環境が提供する一時領域に作成する。ユーザーが指示した場合に限り、対象リポジトリの `tmp/` 配下に配置する。対象リポジトリのルート直下には置かない。

```text
deep-research/20260707-example-topic/
├── plan.md      # リサーチプラン。承認の記録も追記する
├── progress.md  # 進捗台帳。ラウンドごとの定量記録
├── notes/       # サブ質問ごとの調査ノート
├── sources.md   # 参照ソース台帳
└── report.md    # 最終レポート
```

## 依頼の明確化

依頼が曖昧な場合に限り、明確化のための質問を最大 3 問行う。確認すべき典型的な項目は次のとおりである。

- 目的と読者: 何の判断または行動のための調査か、誰が読むか
- 範囲: 対象期間、地域、比較対象、除外事項
- 出力: レポートの言語、想定分量、重視する観点

依頼から自明であれば質問せず、プラン提案へ進む。

## プラン提案

`references/plan-template.md` の形式で `plan.md` を作成し、その内容を会話内で提示する。次の項目を必ず含める。

1. リサーチブリーフ: 依頼を一段具体化した調査目的
2. サブ質問: 5〜10 個。独立して調査でき、全体を合わせると目的を網羅できる構成
3. 調査の深さと停止条件: ラウンド数とソース数
4. レポートアウトライン: 見出し構成と、各セクションに書く内容の 1 行説明

規模は依頼の複雑さに応じて決定する。単純な事実確認寄りなら light、多面的なテーマや意思決定用途なら deep を提案する。

| 規模 | サブ質問 | ラウンド数 | 最低ラウンド | ソース数目安 | 最低ソース |
| --- | --- | --- | --- | --- | --- |
| light | 3〜5 | 1 | 1 | 5〜10 | 5 |
| standard | 5〜7 | 3 | 2 | 10〜30 | 10 |
| deep | 7〜10 | 5 | 4 | 30〜50 | 30 |

最低ラウンドと最低ソースは目安ではなく下限であり、停止判定とレポート執筆の着手条件として用いる拘束値である。所要時間の上限は設けない。スコープ内での広さと正確さを優先する。

提示後、承認を得たら `plan.md` へ承認日時を追記し、`progress.md` を作成して拘束値を転記する。修正指示があれば修正して再提示する。回数は制限しない。

承認前に調査を開始しない。これはユーザーが調査の方向性とコストを制御する唯一のゲートである。

```markdown
# 進捗台帳: <トピック>

- 拘束値: 最低 <N> ラウンド / 最低 <N> ソース（plan.mdより転記）

## ラウンド記録

### Round 1 (<yyyy-mm-dd hh:mm>)

- 対象サブ質問: <番号列挙>
- 実行クエリ数: <N> / 新規ソース: <N> 件 / 累計ユニークソース: <N> 件
- ギャップと次ラウンドの方針: <箇条書き>
```

## 反復調査

承認済みプランのサブ質問を、ラウンド制で深掘りする。この段階は自律的に実行し、ラウンド間でユーザーへ方向性や続行可否を質問しない。承認済みプランが方向性の契約であり、ラウンド内の判断はプランの範囲内で自ら下す。質問してよいのはプラン承認と早期終了承認の 2 箇所に限る。調査の前提自体が崩れた場合のみ、中断して報告する。

各ラウンドの手順は次のとおりである。

1. 状態復元: `plan.md` と `progress.md` を再度読み込む。中断と再開のどちらであっても同じ手順で進められるよう、毎ラウンド必ず行う
2. クエリ設計: サブ質問ごとに表現や切り口を変えた検索クエリを 2〜4 個作成する。判明した事実が増えるほど、固有名詞、バージョン、年号を含む具体的なクエリにする
3. 検索と読解: 有望なソースを選んで読み込み、原文をそのまま貼り付けずに `notes/<NN>-<サブ質問slug>.md` へ「事実、出典URL、確度」の形式で要約する。原文をコンテキスト内に溜め込まないことで、長時間の調査を成立させる
4. ソース台帳更新: `sources.md` へ URL、タイトル、種別、信頼性に関するメモを追記する
5. 内省と記録: notes をプランと突き合わせ、実行クエリ数、新規ソース数、累計ユニークソース数、ギャップ、ソース間の矛盾、次ラウンドのフォローアップ質問を `progress.md` へ追記する。矛盾は両論を確度付きで記録し、一方だけを残して他方を捨てない
6. 絞り込み: 次ラウンドでは対象とする質問数を約半分に絞る。広く着手してから深く絞り込む

### 停止条件

- 通常終了: プランの予定ラウンド数を消化した
- 早期終了: 最低ラウンド数の消化後に限り提案できる。根拠となる数値を `progress.md` へ記録し、ユーザーの承認を得るまでレポート生成へ進まない
    - 飽和: 直近ラウンドの新規ソースが 2 件未満で、notes に新しい事実が追加されなかった
    - 全サブ質問へ確度 high で回答済みであり、累計ソース数が最低ソース数を超えている

最低ラウンド数を消化するまで飽和を宣言しない。初期ラウンドの検索は同じ表層情報を返しやすく、一次資料や実装コードへはフォローアップクエリで初めて到達することが多い。早い段階での飽和判定はほとんどが誤りである。

### ソースの選び方

一次情報（公式ドキュメント、原論文、原コード）、専門メディアや査読記事、個人ブログの順に優先する。検索上位であっても内容の薄いアグリゲータ記事は採用しない。重要な主張は 2 ソース以上で裏付けを取り、単発ソースの主張は確度 low と明記する。

独立したサブ質問は、原則として並列に委譲する。委譲先が多いと Web 検索側のレート制限に達することがある。制限に達した場合は並列数を下げ、その事実を `progress.md` へ記録する。

## レポート生成

執筆を始める前に、`references/report-guidelines.md` を読み、`sources.md` の累計ユニークソース数が拘束値以上であることを確認する。未達の場合は反復調査へ戻る。残りのラウンドがない場合は、追加ラウンドの実施をユーザーへ提案する。

1. 計画時のアウトラインに固執せず、実際の findings に合わせてアウトラインを更新する
2. 全セクションを一括で書かず、セクションごとに notes を参照して執筆する
3. 本文の主張に出典参照を付け、末尾に Sources 一覧を置く
4. 全体を通読し、重複、矛盾、トーンの不一致を修正する

### 機械検証

執筆後、検証スクリプトを実行する。

```bash
node <skillのディレクトリ>/scripts/check-report.mjs --report <作業dir>/report.md --min-sources <最低ソース数> --ledger <作業dir>/sources.md [--check-links]
```

スクリプトは次の項目を検査する。

- Sources のユニーク URL 数が最低ソース数以上であること。重複の判定では、query、fragment、パス末尾のスラッシュを除き、ホスト名の大文字と小文字を区別しない
- Sources の URL がすべて URL として解釈できること
- 本文の脚注参照がすべて Sources 内の脚注定義へ解決し、各定義が URL を含むこと
- 除外見出し以外の本文セクションに、解決する脚注参照または URL があること
- `--ledger` を指定した場合、Sources の URL がすべて `sources.md` にあること
- `--check-links` を指定した場合、Sources の URL へ到達できること

実行結果は、最終行の `RESULT` と終了コードで判定する。

| RESULT | 終了コード | 対応 |
| --- | --- | --- |
| `PASS` | 0 | 完成として報告できる |
| `FAIL` | 1 | FAIL の行を解消するまでレポートを修正する。引数の誤りも終了コード 1 になる |
| `UNVERIFIED` | 2 | ネットワークを利用できず、リンクの到達性を確認できなかった。他の検査は成功しているため、レポートは修正しない。到達性が未検証であることを `progress.md` へ記録し、報告にも明記する |

FAIL のまま完成報告をしない。

スクリプトは記法と対応関係だけを検査する。次の事項は、`references/report-guidelines.md` の品質チェックリストに従って執筆者が確認する。

- 引用先が本文の主張を実際に支持していること
- ソースの品質と信頼性
- `sources.md` の各 URL が、実際に読んだソースとして `notes/` に記録されていること

## 報告

`report.md` のパス、3〜5 行の要旨、確度の低い箇所と未解決の論点、機械検証の結果を報告する。機械検証が `UNVERIFIED` の場合は、リンクの到達性が未検証であることを明記する。

## 制約

- 承認前に反復調査を開始しない
- ラウンド間でユーザーへ方向性を質問しない
- 出典を示せない主張をレポートへ書かない。推測は推測と明記する
- レポートの言語を依頼の言語へ合わせる。指定があればそれに従う
- 中断から再開する場合は、まず作業ディレクトリのファイルを読み込んで状態を復元する
