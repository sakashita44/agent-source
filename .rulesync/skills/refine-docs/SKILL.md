# Refine Docs

書き上げた文書を推敲し、平易で自然なビジネス文書の日本語に整える。推敲の観点と判断基準は `writing-principles` の「推敲」に定め、この Skill は推敲の委譲、修正後の検証、および報告の手順を扱う。

## 起動条件

ユーザーの明示的な指示により使用する。文書作成の完了後、モデルが推敲の要否を判断して起動してもよい。

## 対象

引数が指定されている場合は、指定されたファイル、節、範囲を対象とする。ファイルパスには glob を使用できる。

引数が指定されていない場合は、`git diff --name-only <デフォルトブランチ>...HEAD` に含まれる日本語の Markdown ファイルを対象とする。該当ファイルが存在しない場合は、対象をユーザーに確認する。

## 委譲先

推敲はサブエージェントへ委譲する。委譲先はユーザーの指定を最優先とし、指定がない場合は `subagent` の選択基準に従う。委譲プロンプトの構成、編集内容の確認、失敗時の対応も `subagent` の定めに従う。

## 手順

1. 対象ファイルを読み、推敲前の状態を比較できるようにする。Git 管理下では作業前の `git status` を確認し、Git 管理外では推敲前の写しを保存する
2. サブエージェントへ推敲を依頼する。依頼には次の内容を含める
   - 対象ファイルと推敲範囲
   - `writing-principles` の「推敲」および文体の規則に従い、平易で自然なビジネス文書の日本語に修正すること。委譲先が `writing-principles` を参照できない場合は、該当する規則をプロンプトに含める
   - `writing-principles` の「主体と動詞」に従い、各文の意味上の主体を確認すること。利用者の操作とその結果としてツールが行う処理が 1 文に含まれる場合は、操作を能動態、処理を受動態で書き分けること
   - 意味、事実関係、規範の強度、コード、コマンド、識別子を変更しないこと。意味を変えなければ修正できない箇所は修正せず、問題点として報告すること
   - 節の構成（見出しの追加、削除、統合、分割、移動）を変更しないこと。構成の変更が必要と判断した場合は、対象の節と理由を提案として報告すること
   - 用語を改めた場合は、推敲の対象範囲外も含め、リポジトリ内で同じ用語を用いる全箇所を一括して改め、改めた用語と箇所を報告すること
   - 修正を完遂し、修正前後の文の対比を返すこと
3. 差分を確認し、意味、事実関係、規範の強度、コード、コマンド、識別子が変更されていないことを検証する。用語を改めた場合は、変更前の用語をリポジトリ内で検索し、未修正の箇所が残っていないことを確認する
4. 検証で意味などが変わっていた修正は、その箇所を修正前の表現に戻し、再検討の対象とする。修正が入った箇所は、元の日本語に問題がある可能性が高いため、戻すだけで終えない
   - 再検討の対象を、修正前の文、最初の修正案、変わってしまった点とあわせて同じ委譲先へ 1 回だけ差し戻し、意味を保った修正案を求める
   - 差し戻しても意味を保った修正案が得られない場合は、メインエージェントが意味を保って書き直す。書き直せない場合は、未修正の問題点として報告する
5. 修正後の文書を検証する
   - `write-docs` の機械検査を実行する
   - `natural-japanese` の lint を対象ファイルごとに実行する。`uv` または `natural-japanese` を利用できない環境では、その旨を報告して省略する

     ```bash
     uv run <natural-japanese の Skill ディレクトリ>/scripts/lint.py <対象ファイル>
     uv run <natural-japanese の Skill ディレクトリ>/scripts/lint.py --reading-load <対象ファイル>
     ```

   - 検査の指摘はこの段階では修正せず、`writing-principles` に照らして修正要否を判断し、その判断とともに報告する。自然度スコアは判断基準に用いない
   - `natural-japanese` の文体規則は、次の点で `writing-principles` と食い違う。これらに基づく指摘は、`writing-principles` の該当規則に照らして判断する
     - 文体: ですます調への統一を認める点。`writing-principles` の「日本語の文体」に従い常体を維持する
     - 見出し: 節の結論を見出しへ埋め込む点。`writing-principles` の「読者と内容」に従い、兄弟節との違いと役割が分かる簡潔な名称を用いる
     - 書き手の実感と意見: 書き手の実感や問題意識を加え、意見に「筆者は」を立てる点。`writing-principles` の「分量の配分」および「主体と動詞」に従う
     - 結び: 要約の再統合や次の行動への提言を加える点。`writing-principles` の「分量の配分」に従い、不要な結びを置かない
     - 確信度: 【要確認】などのラベルを付ける点。`writing-principles` の「執筆状態」および「表現」に従い、未解決事項は `TODO:` として局所化する
     - 強調と形式: 太字を文中の核に 1 箇所置き、箇条書きを抑える点。`writing-principles` の「表現」および「形式の選択」に従い、構造に応じた形式を選択する
     - 用語の説明: 同じ用語を複数箇所で説明し直す点。`writing-principles` の「表現」に従い、一度だけ述べる
6. ユーザーへ報告する

## 報告

推敲の採否をユーザーが判断できるように、次の内容を報告する。

- 修正前後の対比: ファイルおよび箇所ごとに、修正前の文と修正後の文を並べて提示する。語句の置き換えのみの修正は、まとめて示してよい
- 再検討した箇所: 修正前の文、最初の修正案と変わってしまった点、最終的な扱い（差し戻し後の修正案を採用、メインエージェントが書き直し、未修正）を示す
- 戻す候補: 再検討を経ても意味や規範の強度が変わった疑いが残る箇所、元の表現のほうが正確な箇所、言い換えの好みが分かれる箇所を、理由とあわせて示す。該当がなければその旨を示す
- 用語の変更: 改めた用語と、推敲の対象範囲外で改めた箇所
- 未修正の問題点: 意味を変えなければ修正できないため、修正を見送った箇所と理由
- 構成の提案: 節の構成変更が必要と判断した箇所と理由
- 検証結果: 機械検査と lint の結果、lint の指摘に対する判断、省略した検査とその理由
