# Verification Principles

## 検証の選択

検証の実施前に、判定基準、その適用範囲、規定元を特定する。規定元と検証手順または補助資料の内容が一致しない場合は、規定元に従って判定し、差異を報告する。

テストで検証する契約は、実装を参照する前に仕様から列挙する。正常時の結果、異常時の振る舞い、仕様が定めていない入力や状態を区別する。仕様が期待値を定めていない箇所は、実装の現状で補わず、設計判断として扱う。

公開契約を新設または変更する際、仕様に未確定の期待値が残る疑いがある場合は、実装は渡さず、仕様と公開インターフェースのみを委譲先へ渡し、検証すべき契約と期待値を決められない箇所を列挙させる。

変更によって起こり得る失敗を事前に特定し、その失敗を観測できる検証を選ぶ。要求された振る舞いが欠けるだけでなく、要求にない振る舞いや副作用が生じることも失敗として扱う。変更の影響範囲、失敗時の損失、復旧の難易度に応じて検証の強度を調整する。

テスト対象は内部実装の分割から機械的に導かず、公開契約、コンポーネント境界、意味のある失敗形態を中心に選ぶ。内部の補助処理は、公開契約の検証を通じて確認する。独立した複雑な純粋ロジック、固有の境界条件、外部システムとの adapter のように、それ自体に独立した契約や失敗形態がある単位は、内部実装であっても直接テストしてよい。

事前に期待値を定められる契約と境界は、自動テストで検証する。文書の不足や設計上の衝突など、事前に仕様として書けない問題は、前提知識で補完しない利用者に実際に使わせて確かめる。

既存のテスト、lint、formatter、pre-commit などの自動化を優先する。自動化によって対象が十分に検証される場合は、同じ検査を手作業で重複させない。対象外の失敗形態には、必要な検証を追加する。原因調査や再現のために作成した一時的な検証は、維持する価値がある場合に限ってテストスイートへ残す。非決定的な探索は通常の CI に含めない。

## テストの設計で陥りやすい形

| 陥りやすい形 | 是正 |
| --- | --- |
| 実装中に起きた個別の不具合を、そのまま回帰テストにする | 不具合から、検証されていなかった仕様または前提を特定し、その仕様に対してテストを設計する |
| 依存ツールの版の違いなど、外部の主体に起因する失敗をテストにする | `engineering-principles` の「データと責務」に従い、版の固定や実行契約で対処できるかを先に判断する |
| エラーメッセージの文面を固定して検証する | 文面が公開契約である場合に限り検証する。それ以外は失敗の種類と終了状態を検証する |
| モジュールや補助関数の分割に沿ってテスト対象を列挙する | テスト対象を、公開契約と意味のある失敗形態の単位へ組み替える |
| 非決定的な失敗の修正を、反復実行の成功で確認する | 「非決定的な失敗の検証」に従う |

## 非決定的な失敗の検証

タイミングや並行性に依存する失敗では、発生機序を検証の対象とする。

1. 発生機序を特定する
2. その機序を決定的に再現する条件を作る
3. 修正前に失敗し、修正後に成功することを確認する

反復実行は、機序を技術的に取り除けず確率的な失敗が残る場合に限って用いる。反復中に別の失敗が発生した場合は、新しい機序の手がかりとして同じ手順で原因を特定する。

## 証拠の扱い

差分だけで成立性を判断せず、変更後の成果物全体に加え、責務、導線、依存関係の判断に必要な関連成果物を確認する。

静的な診断と実行環境での検証を区別する。実行していない検証や観測していない結果を成功とみなさない。テストの成功、件数、試行回数、カバレッジは、検証の十分性の根拠にならない。十分性は、仕様と想定した失敗形態のうち、観測した範囲と未検証の範囲によって判定する。

lint、静的解析、機械的なパターン検出の出力は調査材料として扱い、対象の意味と適用条件を確認した上で欠陥と判定する。

文書と手順の十分性は、前提知識で補完しない読み手が記述だけで遂行できるかによって判定する。検証対象の欠陥と、環境、権限、依存関係に起因する失敗を区別する。

実環境への影響を避ける必要がある場合は、dry-run または隔離した作業環境を用いる。検証後は、実行した内容と結果、未検証事項、残るリスクを報告する。
