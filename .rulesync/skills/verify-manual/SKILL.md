# Verify Manual

文書だけで手順を遂行できるかを検証する。文書本文だけを入力とする計画エージェントに実行計画を作らせ、その計画を実環境へ当てる。

入力を本文だけに制限することが、この検証の中心である。リポジトリやコードを読める実行者は、文書が明示しない手順、前提、パラメータを周辺から補ってしまい、文書の欠落が表面化しない。制限した入力で詰まった箇所が、文書の欠陥の候補になる。

計画エージェントのモデルは指定しない。能力の低いモデルを選ぶと、失敗の原因を文書の不備とモデルの限界へ切り分けられず、判定のノイズが増える。

## 実行条件

ユーザーが明示的に検証を依頼した場合だけ使用する。

## 検証対象の決定

- 第1引数: 対象文書。globを使える。手順を記述したREADMEやセットアップガイドなど
- 第2引数以降: 達成ゴール。省略した場合は、文書が記述する手順自体を遂行対象とする

引数で対象が定まらない場合は、対象を確認して終了する。

想定読者は、対象文書が宣言しているものを使う。外から役割を与えない。文書が読者を宣言していない場合は、その事実を欠陥として報告する。

## 計画立案

1. 対象文書を読む
2. 計画エージェントを起動し、文書本文をプロンプトへ直接渡す
3. 計画エージェントへ次を指示する
    - 渡された本文だけを根拠に、ゴール達成までの手順を分解した実行計画を作る
    - リポジトリ、コード、外部の情報源を参照しない
    - 追加の情報は、手元の記述が名前またはパスで明示的に指す別文書に限り、呼び出し元へ取得を要求できる。明示的に指されていないまま必要になった情報は、詰まりとして記録する
    - 各ステップで実行する具体的なコマンドまたは操作を書く
    - 推測で埋めた箇所、複数の解釈が生じた箇所、情報の欠落で手が止まった箇所を、対応するステップとともに記録する

要求された参照先の文書は、呼び出し元が読んで渡す。

委譲の作法は`subagent`に従う。ツール制限を設定できる配布先では、計画エージェントからファイル読み取りとWeb取得の手段を外す。設定できない配布先では、プロンプトの指示だけが制限の手段になるため、計画エージェントが本文以外を参照した形跡がないかを出力から確認する。

## 実行と照合

計画を作業ディレクトリへ当てる。各ステップを副作用で分類する。

- 安全なステップ: 読み取り、`--help`やバージョン確認、プロジェクトローカルへの依存導入、lint、ビルド、テスト実行など、影響が作業ディレクトリ内に留まり可逆なもの
- 破壊的または外部へ影響するステップ: 削除、リモートへのpushやcommit、デプロイ、公開、外部へのリクエスト、作業ディレクトリ外への変更、グローバル状態の変更

実行するコマンドと、静的な照合に留めるステップを示し、ユーザーの許可を得る。許可を得たものだけを実行する。破壊的または外部へ影響するステップは実行せず、参照するファイル、コマンド、フラグ、手順が実在して整合するかを照合する。

文書にコード例がある場合は、実行できる範囲で出力を照合する。文書が示す期待結果と実際の出力が食い違う場合は、その差を記録する。実行系を用意できない場合は、照合しなかったことを記録する。

各ステップについて、成功または失敗、失敗時のエラー出力、文書にない推測が必要だったか、参照先が実在したかを記録する。

## 欠陥の切り分け

実行結果と詰まりの記録を突き合わせ、各事象を切り分ける。

1. 詰まりの記録にある箇所か。記録になければ、文書の欠陥ではない可能性が高い
2. 文書の記述を追加すれば解消するか。解消するなら文書の欠陥である
3. 記述を追加しても解消しないか。環境の依存、設定の差異、対象の不具合であれば環境起因である

詰まりの記録を主たる根拠とし、実行の失敗で裏付ける。実行が失敗しても詰まりの記録に対応がない場合は、環境起因として扱い、文書の欠陥として報告しない。

## 出力形式

```markdown
## verify-manual 結果

### 対象
- 文書: <ファイル>
- 想定読者: <文書が宣言しているもの>
- ゴール: <ゴール、または文書が記述する手順>

### 文書の欠陥
- [該当ステップ] 欠陥の内容（推測・曖昧・欠落・誤り）と、不足している記述
    - 補うべき記述

### 環境起因
- [該当ステップ] 環境側の事象

### 照合しなかった箇所
- [該当ステップ] 実行しなかった理由

### 総合: PASS / FAIL（N 件の文書の欠陥）
```

文書の欠陥がない場合は、文書だけでゴールを遂行できたと報告する。
